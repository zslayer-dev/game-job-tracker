# 구현 계획 — 작업 목록

설계 근거는 [design.md](design.md). `#번호`는 PRD 10장 검증 기록 번호. 각 단계는 "완료 조건"을 확인한 뒤 다음으로 넘어간다.

## Must

### M0. 프로젝트 뼈대와 빈 배포
- Vite + React + TS(`web/`), Supabase CLI 초기화(`supabase/`), `.gitignore`에 `.env*`
- Supabase 프로젝트 생성, Vercel에 빈 페이지 배포, `vercel.json` SPA 재작성
- 완료 조건: 배포 주소에서 빈 화면이 뜬다
- 검증: (선행 작업 — 이후 모든 검증이 배포 주소에서 이뤄짐)

### M1. 구글 로그인·로그아웃 + OAuth 프로덕션 게시
- Google OAuth 클라이언트, Supabase Google 공급자, Site URL·Redirect URLs 설정
- 로그인 화면, 로그아웃 버튼, 로그인 여부에 따른 라우팅
- **OAuth 앱을 이 단계에서 바로 "프로덕션"으로 게시** — 막히면 일찍 알아야 시연 영상 대안을 준비할 수 있음
- 완료 조건: 시크릿 창에서 배포 주소 로그인 → 배포 주소로 복귀, 테스트 사용자 아닌 계정도 로그인
- 검증: **#9, #10**

### M2. applications 표 + 권한 (마이그레이션)
- 표·CHECK 제약·`updated_at` 트리거·`unique(id, user_id)`·정렬 인덱스
- RLS 4개 정책, `anon` 권한 회수
- 로컬 테스트 스크립트: 두 사용자 교차 조회·수정·삭제, 로그아웃 조회·추가, 빈 회사명 insert
- 완료 조건: 스크립트에서 교차 요청은 0건·DB 불변, 로그아웃은 권한 오류, 빈 값은 제약 오류
- 검증: **#4(DB 쪽), #5, #6**

### M3. 지원 건 CRUD 화면
- 목록 표(회사·포지션·상태·지원일·마감일), 추가·상세·편집 화면(모든 필드), 삭제
- 상태 드롭다운: 8개 선택지 자유 변경, 지원 경로 드롭다운
- 화면 쪽 입력 검사: 회사·포지션 필수, 공고 원문 8,000자 카운터
- 완료 조건: 배포 주소에서 추가·수정·삭제·상태 앞뒤 변경 후 새로고침·재로그인해도 유지
- 검증: **#1, #2, #4(화면 쪽)**

### M4. 목록 필터·정렬·검색
- 상태 필터, 지원일 최신순 + 빈 값 맨 아래 + 그 안에서 생성 최신순(DB 쿼리)
- 회사명 검색(`ilike`) — *일정이 밀리면 Should로 내림(PRD 5장 주석)*
- 완료 조건: 지원일 있는 건 2개 이상 + 빈 건 1개 이상 + 상태 다른 건으로 확인
- 검증: **#3**

### M5. 샘플 데이터 채우기
- DB 함수 `seed_sample_data()` (사용자별 advisory lock → 비어 있는지 확인 → 6건 insert), 실행 권한 `authenticated`만
- 가상 회사·공고 원문 작성(지원일 빈 건, 상태 다양하게)
- 빈 상태 화면: 안내 문구 + 추가 버튼 + 샘플 버튼. 지원 건이 있으면 버튼 숨김
- `tests/seed-concurrency`: 같은 계정으로 동시 10건 요청
- 완료 조건: 새 계정 두 개로 각자 채우기 → 서로 안 보임, 재요청 거부 / 동시 요청 시 6건만
- 검증: **#7, #8**

### M6. 화면 공통 상태
- 로딩 표시 + 처리 중 버튼 비활성화(중복 클릭 방지), 저장 실패·권한 거부 짧은 오류 문구
- *세부 표현은 일정이 밀리면 Should로 내림(PRD 5장 주석). 최소한 중복 클릭 방지는 M5 전에 넣는다 — 샘플 버튼 연타 방지*
- 검증: (직접 대응하는 번호 없음, 6장 공통 요구)

### M7. Must 검증 및 기록
- 배포 주소에서 #1~#10 수행, PRD 10장 "결과" 칸 갱신, README 작성("구글 계정으로 로그인 필요", OAuth 게시 상태)
- 검증: **#1~#10 전체**

## Should

### S1. 경력 프로필
- `profiles` 표 + RLS + `anon` 권한 회수 + `is_profile_empty()`
- 프로필 화면(경력 요약, 주력 엔진, 기술 스택, 강점, 보완점)
- `seed_sample_data()` 교체: 프로필이 비어 있으면 가상 프로필도 채움
- 완료 조건: 저장·새로고침 유지, 다른 계정에서 안 보임, 빈 계정 샘플 채우기 시 프로필도 생성
- 검증: (#11의 선행 조건. 프로필 격리는 #5와 같은 방식으로 추가 확인)

### S2. AI 관련 표와 한도 함수 (마이그레이션)
- `ai_analyses`(복합 FK, 연쇄 삭제), `ai_usage`(결과·사유 CHECK)
- RLS: ai_analyses 본인만 / ai_usage 본인 조회만, 쓰기 권한 회수
- `counts_for_user()`, `begin_ai_call()`, `finish_ai_call()`(service_role만), `my_ai_remaining()`
- SQL 수준 테스트: 낮은 한도로 동시 `begin_ai_call` 호출, 2분 지난 진행 중 행, 사유별 집계
- 검증: **#17**, #12·#13·#14·#15·#16의 DB 쪽

### S3. Edge Function `analyze-posting`
- JWT 검증 → 지원 건(RLS) → 원문 길이 → 프로필 비어 있음 → `begin_ai_call` → AI 호출(60초) → 형식 검증 → `finish_ai_call`
- AI 키·한도는 `supabase secrets`, `AI_MOCK`은 로컬만
- 착수 시 Claude API 모델 ID·구조화 출력 방식을 공식 문서로 확인
- 검증: **#12, #15, #18, #19**(서버 쪽)

### S4. AI 분석 화면
- 상세 화면에 분석 버튼, 진행 중 표시, 결과(적합도·매칭·부족·코멘트), 저장 버튼, 최신 저장 결과 표시
- 오늘 남은 횟수(`my_ai_remaining()`), 오류 코드별 문구(사용자 한도 / 전체 한도 / 프로필 없음 / AI 실패 / 형식 오류)
- 완료 조건: 데모 공고로 분석 → 저장 → 새로고침 후 남음
- 검증: **#11**, #12(문구 구분)

### S5. Should 검증 및 기록
- 한도 낮춘 설정 + `AI_MOCK`으로 동시 요청 테스트: 같은 사용자(#13), 다른 사용자(#14)
- 사유별 실패 흉내(#15), 멈춘 진행 중 기록(#16), 직접 쓰기 요청(#17), 깨진 응답(#19)
- 저장소 `git grep` + 배포 번들 검색(#18)
- PRD 10장 결과 갱신, README 보완
- 검증: **#11~#19 전체** (우선순위상 #19가 최하위 — 시간이 없으면 마지막에 남김)
